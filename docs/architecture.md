## ساختار مخزن

```text
torob-challenge/
├── backend/
│   ├── config/            تنظیمات Django و مسیرهای اصلی
│   ├── core/              سلامت، آدرس، اتصال AI و پنل
│   ├── catalog/           مدل داده، import و جستجوی فروشگاه
│   ├── agent/             گفتگو، worker، ابزار، دانش و پاسخ تصویری
│   ├── requirements.txt   نسخه‌های Python
│   ├── gunicorn.conf.py   تنظیمات وب پروداکشن
│   └── Dockerfile
├── frontend/
│   ├── src/               رابط React و کامپوننت‌ها
│   ├── public/            فونت‌ها و تصاویر رابط
│   ├── scripts/           تولید قرارداد مشترک ویجت‌ها
│   ├── nginx.conf         سرو فایل و انتقال API در پروداکشن
│   └── Dockerfile         مراحل توسعه، build و Nginx
├── dataset/               محل CSVها؛ فایل خام داخل Git نیست
├── docs/                  راهنماهای تخصصی
├── .env.example           نمونهٔ تنظیمات بدون کلید واقعی
├── compose.yaml           اجرای توسعه
└── compose.production.yaml اجرای مستقل پروداکشن
```

CSSهای رابط کنار همین بخش‌ها نگهداری می‌شوند. تغییرات باید در هر دو تم و عرض موبایل بررسی شوند. فونت و تصویر از فایل‌های پروژه خوانده می‌شوند؛ سرویس فونت آنلاین برای نمایش اولیه لازم نیست.

## مسیر یک پیام

1. مرورگر متن یا action کارت را با شناسهٔ درخواست می‌فرستد.
2. Django نوبت را برای همان نشست در PostgreSQL ثبت می‌کند.
3. worker نوبت را claim و در فرزند محلی اجرا می‌کند؛ Redis یا صف خارجی اضافه وجود ندارد.
4. عمل شناخته‌شدهٔ کارت مستقیم اجرا می‌شود؛ سایر پیام‌ها به گردش مدل و ابزار می‌روند.
5. ابزار دادهٔ واقعی و محدود برمی‌گرداند؛ پاسخ تصویری از evidence ساخته و اعتبارسنجی می‌شود.
6. مرورگر وضعیت نوبت را دریافت و ویجت‌های مجاز را RTL نمایش می‌دهد.
7. دکمهٔ نقشهٔ هر پیام، فروشگاه‌های همان پیام را مجدداً فعال و قاب نقشه را تنظیم می‌کند؛ فروشگاه‌های هم‌مکان از فهرست جدا هم انتخاب می‌شوند.

Stop وضعیت نوبت را لغو و پردازش فرزند را قطع می‌کند؛ نتیجهٔ دیررس نمی‌تواند لغو را بازنویسی کند. deadline شامل صف هم هست. اگر نتیجهٔ معتبر قبل از قطع ذخیره شده باشد، امکان تکمیل بر اساس همان داده وجود دارد؛ در نبود نتیجه، خطا شفاف نمایش داده می‌شود.

## محل ماندگاری اطلاعات

| اطلاعات | محل |
| --- | --- |
| کاتالوگ، تنظیمات پنل، آدرس‌ها، نوبت‌ها و محصولات ذخیره‌شده | PostgreSQL در volume |
| فروشگاه‌های ذخیره‌شده و تم | localStorage مرورگر |
| پیش‌نویس مبلغ هر ویجت | localStorage؛ بودجهٔ ثبت‌شده در زمینهٔ گفتگو نیز ذخیره می‌شود |
| مالکیت دسترسی مرورگر | نشست/cookie؛ سیستم حساب مشتری سراسری پیاده نشده |
| کلید پیش‌فرض | `.env` خارج Git |
| کلید جایگزین پنل | رمز‌شده در دیتابیس، وابسته به `DJANGO_SECRET_KEY` |

پروفایل embedding در پنل پشتیبانی می‌شود، اما مسیر فعلی بازیابی محصول متنی و مبتنی بر PostgreSQL است. سرویس بیرونی فقط برای مدل، نقشه و آدرس معکوس مورد نیاز است؛ لینک مسیر خیابانی جدا باز می‌شود.


## بستهٔ استقرار PaaS لیارا

برای انتشار با CLI، `Dockerfile.liara` در ریشه سورس فرانت را build و همراه بک‌اند در یک image قرار می‌دهد. `deploy/liara/nginx.conf` روی پورت 8080 فایل‌های فرانت و static را ارائه می‌کند و درخواست‌های API را به Gunicorn همان کانتینر می‌فرستد. `deploy/liara/supervisord.conf` وب، Nginx و worker را اجرا و در صورت خروج دوباره راه‌اندازی می‌کند. `start.sh` پیش از آن migration و آماده‌سازی فایل‌های static را انجام می‌دهد.

این مدل مخصوص دموی محدود در یک replica است؛ سرویس PostgreSQL جدا می‌ماند و داده با filesystem موقت برنامه از بین نمی‌رود. `scripts/liara.py` ابزار انتشار محلی است و به پردازش runtime اضافه نمی‌شود. `liara.json` و دو فایل ignore تنظیمات عمومی انتشار و مرز فایل‌های ارسالی‌اند. مسیر Compose توسعه/پروداکشن قبلی همچنان مستقل کار می‌کند.
